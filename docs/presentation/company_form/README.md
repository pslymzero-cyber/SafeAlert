## 비용 장 — 무엇을 주장하고 무엇을 주장하지 않는가

현장 현행 장비는 **I-PAS** 다. 단가와 수량은 사용자 제공 (2026.08 기준).

| 항목 | 단가 | 일반 WF 센터 수량 | 금액 |
|------|------|------------------|------|
| 차량 태그 | 525,000원 | PIT 4대 | 2,100,000원 |
| 보행자 태그 | 110,000원 | 상시 3명 | 330,000원 |
| EOD | 220,000원 | 수량 미확정 | 별도 산정 |
| **합계 (EOD 제외)** | | | **2,430,000원** |

상시 5명 센터는 2,650,000원. 확산 환산은 5개 1,215만 · 10개 2,430만 · 15개(FFWF 전체) 3,645만원.

포지셔닝은 **우선 보완, 검증 후 판단**이다. 그래서 이 장은 대체 절감액을 주장하지 않는다.
주장하는 것은 하나다 — *I-PAS 가 덮지 않는 구간(보행자끼리 · EPJ · 미장착 장비)을 추가
하드웨어 없이 덮는다.* 환산 금액은 **절감액이 아니라 같은 범위를 하드웨어로 덮을 때의
금액 규모**이며, 슬라이드에 그대로 적었다.

세 가지 전제를 슬라이드 하단에 명시한다 — 단가는 사용자 제공 기준이라는 것, 앱이 0원인
이유가 단말이 이미 지급돼 있기 때문이라는 것(미지급 인원은 BLE 태그 지급이 필요), 대체
여부는 이번 요청 범위 밖이라는 것. 이 세 줄이 없으면 안전 부서에서 동등성 주장으로 읽힌다.

산출 과정은 **13장 부록**으로 뺐다 (CouSolve 자료의 08 부록 방식) — 금액을 주장하는 장과
계산을 분리해야 숫자를 검증하려는 사람이 볼 곳이 분명해진다. EOD 는 수량 기준이 확인되지
않아 합계에서 제외했고, 그 사실도 적었다.

한 장 요약의 지표 2번도 `인프라 0` → `추가 하드웨어 0 / I-PAS 1세트 약 54만원 대비` 로 바꿨다.

## 한 장 요약과 요청 사항

리더십에서 "무엇을 어필하고 싶은지 모르겠다"는 지적이 나와 앞뒤 두 장을 붙였다.
그전 덱은 배경 · 기대효과 · 장단점 · 피드백 · 안돈이 고르게 놓인 **균형 잡힌 현황 보고**였고,
주장도 요청도 없었다. 균형은 정직해 보이지만 결정을 요구하지 않는다.

- **3장 한 장 요약** — 핵심 문장 한 줄(`사각지대를 사람의 주의력에 맡기지 않는다`),
  지표 넷(3개월 · 70회+ / 인프라 0 / 리뷰 3차 · 요구 4건 / 로드맵 1-5), 그 아래 요청 상자
- **11장 요청 사항** — `무엇을 / 왜 필요한가 / 없으면` 3열. 요청은 **정식 과제 등록과 리소스 배정**
  (유지보수 주체 · 개발 시간 · 현장 검증 슬롯 · 보안 검토). `없으면` 열이 요청의 근거를 진다

장단점 장에도 리드인 한 줄을 넣었다 — "넷 다 의도한 선택이다". 트레이드오프 네 행이
결함 목록으로 읽히는 것을 막는다.

요청 내용의 근거 — 유지보수 주체 미지정과 기술 부채는 `.planning/PROJECT.md` Active
(`BleService` 3,899줄 단일 클래스 · 분산 상태 40여 개), 현장 검증 슬롯은 `ROADMAP.md`
Overview(검증 사이클이 현장 가용 시간에 묶임), 보안 2건은 `.claude/CLAUDE.md` Security.

## 표현 장치 — CouSolve Idea Contest 에서 가져온 것

폼은 사내 표준(LFP)을 그대로 쓰되, 슬라이드 안쪽 표현은 `2026 CouSolve Idea Contest` 자료의
장치로 바꿨다. 그 자료의 7단계 프레임워크(Problem Statement → Tradeoffs → … → Feedback Loop)를
그대로 따르지는 않는다 — 지금 목차에 맞는 장치만 골라 옮겼다. 코드는 `_devices.py`.

| 장 | 바꾼 것 | 가져온 장치 |
|----|---------|-------------|
| 1. 개발 배경 | ①②③ 나열 → 회색 라벨 + `AS-IS / Pain Point` · `Data / Issue` | Problem Statement |
| 2. 기대효과 | ①~⑥ 나열 → `구분 / As-is / To-be` 3열 표 | GOAL 의 As-is·To-be |
| 3. 장단점 | 장점 5 · 단점 4 나열 → `A vs. B → 택한 것` + 화살표 + 판단 근거 4행, 그 아래 `남는 한계` | Tradeoffs |
| 4. 사용자 피드백 | 나열 → `차수 / 반영 내용 / 결과` 표 + `항목 / Before / After` 표 | Feedback Loop |
| 5. 시연 | 목록 → `신호 수신 → 거리 추정 → 등급 판정 → 3중 경보` 흐름 한 줄 (아래에 기술 요소) | Solution |
| 6. 진행 단계 | 신설 — `단계 / 무엇을 / 확인할 것 / 상태` 표 | Feedback Loop 의 확산 계획 |
| 7. Andon | 신설 — `Andon 기준` · `조치 방법` 좌우 배치 | Andon |
| 1장 하단 | — | 번호 매긴 한 줄 요약 + 이탤릭 결론 문장 |

장단점을 트레이드오프로 바꾼 것이 가장 큰 변화다. 단점을 결함 목록으로 늘어놓는 대신
**무엇을 얻으려고 무엇을 내줬는지**로 적으면, 같은 사실이 변명이 아니라 설계 판단으로 읽힌다.
반대로 트레이드오프가 아닌 것(미설치 기기 비감지 · 밀집 시 지연)은 `남는 한계`로 따로 뺐다.

## 안드로이드 전용인 이유

장단점 4번째 트레이드오프의 근거다.

| 막히는 것 | 왜 |
|-----------|-----|
| 역할 · 상태를 실은 광고 송출 | iOS 는 백그라운드 진입 시 서비스 UUID 를 오버플로 영역으로 옮기고 제조사 데이터를 싣지 않는다. 1바이트 페이로드(CAT/STATE/TURN/RISK)가 상대에게 도달하지 않는다 |
| 화면 꺼짐 상태 상시 스캔 | 안드로이드는 포그라운드 서비스 + 지속 알림으로 유지한다. iOS 에는 대응물이 없다 |
| 화면 가장자리 경보 사이드바 | `SYSTEM_ALERT_WINDOW` 는 안드로이드 전용. iOS 는 다른 앱 위에 그릴 수 없다 |
| 알람 스트림 경보음 | 백그라운드에서 알람 볼륨으로 소리를 내는 경로가 iOS 에 없다 |

**대응책은 이미 코드에 있다.** `BleScanner.buildFilters()` 가 SafeAlert 서비스 UUID 외에
등록 비콘을 서비스 UUID · MAC · iBeacon 제조사 ID(0x004C) 로 함께 스캔한다
(`02_ble/BleScanner.kt:303-337`). iOS 인원에게 BLE 태그를 지급하면 안드로이드 단말이 그 태그를
감지 대상으로 잡는다 — 페이로드가 없으므로 `CAT 00`, 즉 보행자로 판정된다
(`02_ble/BleConstants.kt:97`). 세이프존 비콘이 이미 같은 경로를 쓴다.

다만 **이 용도의 현장 검증은 아직 없다.** 존 비콘으로만 써 봤다.

## 시연 영상의 경보음

헤드리스 크로미움은 화면만 녹화하고 소리는 담지 못한다. 그래서 `record_demo.js` 는
시뮬레이터가 경보음을 낸 **시각**을 받아 적어 두고(`AudioContext.createOscillator` 후킹),
녹화가 끝난 뒤 같은 음을 그 자리에 얹는다.

- 음은 `sim/sim.js` 의 `beep()` 을 그대로 옮겼다 — square 파형, 위험 1180Hz · 경고 760Hz,
  10ms 상승 후 150ms 지수 감쇠, 180ms 정지. 발령 간격도 위험 320ms · 경고 900ms 로 같다
- 녹화 시작 지연은 `(닫은 시각 − 기준 시각) − 영상 길이` 로 재서 보정한다
- 소리 크기만 슬라이드쇼에서 들리도록 정규화했다 (원래 gain 0.08)

**이 소리는 시뮬레이터의 경보음이지 실제 단말 녹음이 아니다.** 앱은 안드로이드
`ToneGenerator` 의 CDMA 톤(경고 `TONE_CDMA_ALERT_CALL_GUARD`, 위험
`TONE_CDMA_EMERGENCY_RINGBACK`)을 쓰므로 음색이 다르다. 실제 소리를 넣으려면
단말 화면 녹화본이 필요하다. (`res/raw/alert_warning.wav` · `alert_danger.wav` 는
서로 바이트까지 같은 미사용 파일이라 쓰지 않았다.)
