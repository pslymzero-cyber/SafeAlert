- **`UWB_MEAS_FRESH_MS` 는 `private val` 상수(BleService.kt:682, 값 1_000L).** 테스트에서 이 값을 리터럴로 재선언하지 말고, 테스트 상수에 이름을 붙여 한 곳에서만 정의하고 그 이름을 쓴다. 프로덕션 상수가 바뀌면 골든이 깨지는 것이 **의도된 동작**이다 — 자동 추종 금지.
- **두 시계가 공존한다.** `uwbJudgeModeExclusive(deviceId, now)` 는 `processAlert` 의 시임 시계(`nowMs`)에서 온 `now` 를 받고, `freshUwbDistM` 은 `System.currentTimeMillis()` 를 직접 읽는다(BleService.kt:2569). D-4C 가 정한 대로 **차이(now - sampleAt)만이 판정에 쓰이므로** 두 시계를 통일할 필요는 없고, 대신 아래 규칙을 지킨다:
  - 시나리오 앵커 `T0_MS` 는 테스트 시작 시점의 `System.currentTimeMillis()` 로 잡는다. `nowMs` 시임은 이 앵커 기반 값을 돌려준다.
  - **신선 표본은 미래 오프셋으로 주입한다** (`sampleAt = T0_MS + FRESH_OFFSET_MS`, 예: +500ms). D-4C 의 Known gap(실행이 느려지면 신선 케이스가 1s 를 넘겨 플레이키)에 대한 마진 확보다. `now - sampleAt` 이 음수여도 `<= UWB_MEAS_FRESH_MS` 는 성립한다.
  - **낡은 표본은 과거 오프셋으로 주입한다** (`sampleAt = T0_MS - STALE_OFFSET_MS`, 예: -2000ms). 두 시계 어느 쪽으로 재도 낡음이 흔들리지 않는 마진이다.
  - **경계 정밀 판정(999/1000/1001ms)은 `freshUwbDistM` 를 경유시키지 않는다.** 벽시계 드리프트가 1ms 판정을 흔들기 때문이다. 경계는 `uwbJudgeModeExclusive(deviceId, now)` 를 명시적 `now` 로 직접 반사 호출해 검사한다 — 이 경로는 인자로 받은 시각만 쓰므로 드리프트가 없다.
- **`DevSettings` 키 두 개는 하네스 범위 밖이다.** `applyGoldenDevSettings()` 는 `processAlert` 본문(1406-2543)이 참조하는 키만 세팅한다. `uwbExclusiveJudgeEnabled`(BleService.kt:2555)와 `walkerDetectsWalker`(judgeUwbOnly 내부)는 그 범위 밖이므로 **이 테스트 파일에서 명시적으로 세팅**한다. 하네스를 고쳐서 해결하지 않는다.
- **세션 기기 수 상한 이하만 다룬다.** `UwbRanger.MULTICAST_MAX`(UwbRanger.kt:77, 값 6)를 넘는 경로는 BUG-03 으로 v2 이월됐다. 상한을 넘는 시나리오를 골든으로 고정하면 버그를 스펙으로 승격시키게 된다(REQUIREMENTS.md v2 BUG-03 근거 원문). 기기 수는 런타임 `require` 로 상한 이하임을 강제한다.
- **record-then-freeze (Phase 1 D-09 계승).** 값은 1회 기록 후 동결. 자동 갱신 경로(`-PupdateGolden` 류)를 만들지 않는다. 동결 전 파라미터 조정은 허용, 동결 후 기대값 수정은 사용자 판단을 받는다.
